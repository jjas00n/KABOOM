# 성능 측정 기록

## 2026-10-26 — 붕괴 후 FPS 저하 (Phase 3 → Phase 4 전)

증상: Medium 건물(Bodies 3743)을 많이 부수면 FPS 9~11. 목표 55fps 이상.

### 측정 방법

- 건물: seed 1, 6층, 4×3칸, Medium (부재 737 → 조각 3742 + 지면 = 바디 3743)
- 브라우저: headless Chrome + ANGLE D3D11 (실제 GPU, RX 6800). CPU는 그대로(x1) 또는
  DevTools CPU 스로틀 2배(x2). **x2가 사용자 증상(9~11fps)을 그대로 재현**해서 x2를 기준으로 본다.
- 디버그 GUI `Perf` 폴더 (0.5초 구간 프레임당 평균):
  Frame / Physics / Steps per frame / Update / Sync / Render(CPU 제출 시간) ms,
  Fixed / Dynamic / Awake / Sleeping 바디 수, Contact pairs(실제 접촉점이 있는 쌍)
- 시나리오
  - **Smash test**(디버그 GUI 버튼): 모든 층 정면+오른쪽 외벽 42곳을 한꺼번에 폭파 → 조각 1290개 동시 dynamic.
    최악 경우. 폭파 직후 0.5s / 1s / 3s / 10s 값을 읽는다.
  - **클릭 시나리오**: 건물 위 고정 지점 30곳을 0.5초 간격 클릭(15초) + 이후 5초. 실제 사용에 가까움.

### 결론과 남은 것

- 원인: 잔해가 잠들지 않음(더미 = 하나의 island) + spiral(최대 5스텝)로 증폭.
- 해결의 핵심: 느려진 조각을 **fixed로 굳혀 시뮬레이션에서 빼기** (`DebrisManager`).
  굳은 조각은 다시 맞으면 `FragmentSet.activate`로 깨어난다.
- 남은 한계: 1000개 이상이 **한 프레임에** 동시에 dynamic이 되는 최악 경우, 느린 CPU(x2)에서
  처음 2~3초는 14~20fps(물리는 그동안 실시간의 절반 속도 = 자연 슬로모션). 대포 한 발은 이보다 훨씬 작다.
- Phase 4 주의:
  - 지지 상실로 떨어지는 섬(island)은 compound 강체 1개로 떨어뜨려야 동시 dynamic 수가 안 폭증한다(ROADMAP 계획대로).
  - 굳힌 잔해 아래 조각이 나중에 빠지면 잔해가 공중에 뜰 수 있다 → CollapseSolver가 굳힌 잔해도 지지 검사 대상에 넣을 것.
- 렌더 CPU는 3~8ms로 여유. 붕괴 중 병목 아님.

## 2026-10-26 — Phase 4 구조 붕괴 도입 후

같은 환경(seed 1, 6층 4×3, Medium, RX 6800, headless Chrome). Phase 4부터 클릭은 반경 고정 활성화가 아니라
**에너지 기반 폭발**(1.6MJ ≈ 반경 3.5m) + 지지 상실 붕괴 + 충돌 연쇄라서 같은 클릭 수에도 파괴량이 Phase 3보다 많다.

### 붕괴 판정 비용과 대응

- 지지 거리(Dijkstra) 0.8ms + 하중 계산 2.1ms (x1, 노드 3742 / 엣지 12475).
- 모서리 한 방 뒤 10초 동안 엣지가 계속 끊겨 스텝의 36%에서 재계산 → 스텝당 평균 1ms.
- `STRUCTURE.solveIntervalSec = 0.1`로 재계산을 묶음 (폭발 직후만 즉시). x2 클릭 중 평균 44 → 53fps.

### 시도하고 버린 것

- 작은 조각 cuboid 비율 30% → 60%: 빨라 보였지만(x2 56fps) 파괴량 자체가 달라져(남은 바디 3607 vs 3184) 공정 비교가 아님 + 모양 차이. 보류.
- 접촉 예측 거리 2cm → 0.5cm: 차이 없음.

### 결과 (클릭 시나리오: 0.5초마다 30번)

|                     | x1 클릭 중 / 후 | x2 클릭 중 평균(최저) | x2 클릭 후 평균(최저) | x2 Physics / Render ms |
| ------------------- | --------------- | --------------------- | --------------------- | ---------------------- |
| Phase 3 (붕괴 없음) | 60 / 60         | 59.9 (58)             | 60 (60)               | –                      |
| Phase 4             | 60 / 60         | 57.1 (28)             | 47.8 (39)             | 8.6 / 5.6              |

- 클릭 후에도 점진 붕괴(과부하 엣지 손상 누적)와 떨어지는 덩어리가 계속 움직여 x2에서 50fps 전후.
  x1(데스크톱 실 CPU)에서는 모든 시나리오 60fps 유지.
- 최악 시나리오 "Pull front columns"(뒤쪽 1층 기둥 줄 제거 → 그쪽 전체가 무너짐): x1 60fps, Physics 최대 11.5ms.

### Phase 5 이후 후보

- 덩어리(compound) 콜라이더 수가 많으면 접촉 비용이 크다 → 덩어리는 조각 hull 대신 단순 박스 몇 개로 근사.
- 하중 계산 정렬(Float32 비교 정렬)을 버킷/기수 정렬로.

## 2026-10-27 — Phase 6 사실적 그래픽 (텍스처·HDRI·후처리·이펙트)

### 측정 환경과 한계

  묶여 있어 **절대 FPS는 의미가 없고, 같은 조건의 전후 차이만** 본다.
- 건물: seed 1, 6층, 4×3칸, Medium. 카메라 고정(34, 16, 30 → 건물 중심). 멀쩡한 건물(idle).

### 더 줄여야 하면

1. `FIRE.weakenRate`를 낮추거나 `minStrength`를 높인다. 붕괴가 늦고 덜 일어나 동시 dynamic이 준다.
2. `FIRE.maxBurning`를 900에서 500으로. 확산이 느려지고 동시에 약해지는 층이 준다.
3. Phase 4 후보(덩어리 콜라이더 단순화)가 그대로 화재 붕괴에도 듣는다.

## 2026-10-27 — 손상 외관 (틈·균열·느슨한 조각) + "보이는 조각은 반드시 맞는다"

### 통과 원인 진단 (재현 테스트, 6층 Medium seed 1, 같은 조준 4발)

- 4발째 경로의 첫 콜라이더: **굳은(fixed) 잔해, 그룹 `0x4fffd`(debris), 원래 자리에서 0.37m**.
  발사체 필터로는 이걸 건너뛰고 7.6m 안쪽의 서 있는 조각에 처음 맞았다 → **(b) 충돌 그룹** 확정.
  굳은 잔해 69개 중 54개가 원래 자리 0.3m 안(= 멀쩡해 보이는데 통과).
- (a) 콜라이더 없는 조각 0, (c) 렌더↔바디 오차 0mm, (e) CCD 켜짐 — 해당 없음.
